## 关键设计决定

- `algorithms` 只接受服务端配置的算法，不信任 token header，防止算法混淆攻击。
- PyJWT 异常不会直接泄露给上层，统一转换为过期或无效两类业务异常。
- JWT payload 可被 base64url 解码查看，因此只放身份 subject 和过期时间，不放密码等敏感数据。
- 验签只依赖服务端密钥，不查数据库，保持 token 校验的无状态特性；鉴权依赖留给 D09。

### 老师讲解 / 我的复述记录
**学生原理解（带教前）**：JWT 三部分但只懂 payload 放用户信息、signature 验真伪，header 含义不清；认为 JWT 起安全作用但理解停在表层。

**老师补全/纠偏**：
1. Header = 元数据（`alg`/`typ`），告诉服务端用什么算法；三段的职责一句话：Header 说"用啥算法"、Payload 装内容（能读）、Signature 是密钥钢印（防改）
2. 安全靠**签名不靠保密**：base64url 可解出明文，所以"能看不能改"，密码等敏感数据绝不可进 token
3. 验签 = 本地用 SECRET_KEY 重算 HMAC 比对，**不查库**（无状态真义）；密钥泄露则一切可伪造
4. `algorithms=[settings.jwt_algorithm]` 写死 = 防算法混淆（alg=none 攻击）
5. 过期 vs 无效分开（TokenExpiredError/TokenInvalidError）→ 未来 401 vs 403 语义不同
6. decode 后仍 `isinstance(sub, str)` 补查：require 只保证 key 存在，不保证 sub 是合法字符串
7. 测试为何手工 `jwt.encode` 拼坏 token：create_access_token 永远给未来时间，造不出过期/缺字段

**面试结论**：JWT 值得"概念级详细了解"（三段+安全+验签不查库+算法白名单），不必深挖 HMAC 实现细节。

**验证实录**：pytest `16 passed`（D04-D08 全量回归，含 test_token 5 条全绿）；亲眼确认篡改/过期/错密钥/缺 sub 均正确抛错。

### 概念补遗（SECRET_KEY / HMAC / 算法白名单，2026-09-09 追加）
1. **SECRET_KEY**：服务端专属"身份私章"，**全服务共用一个**（非每用户独有；用户身份在 token 的 sub 里）。配在 `.env`（D07），泄露才需更换（换后旧 token 全失效）。类比：学校一枚钢印盖所有学生证，验证"本校所发/未被改"，不区分张三李四。
2. **HMAC 签名**：拿密钥对 header.payload 算固定长度"指纹"（=内容+密钥一起算）。作用三件：防篡改（改一字指纹变）、防伪造（无密钥算不出合法指纹）、验证来源。**对称**——签发与验证用同一把 SECRET_KEY（HS256 的 S=Secret）。
3. **算法白名单**：服务端只认 `algorithms=[自己配置]`，其余默认拒绝。防**算法混淆攻击**（攻击者把 Header 的 alg 改成 none 声称不用签名来伪造身份）。本质=验证规则由服务端定、不由客户端自述定，**不信 token 自述、只信自己配置**。
