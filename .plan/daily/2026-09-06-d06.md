### 补充（Claude，2026-09-11 追加）：Schema 校验 vs Service 校验 —— 三层校验的判据

学生在 M0+M1 阶段总结时提问：「Schema 里的校验和 Service 里的校验是一个东西吗？」——**不是，这是两种性质的关卡**。补记于此。

**唯一判据：需不需要「问别人」。**
- 只看这条数据本身就能判断（不依赖任何外部状态）→ **Schema**。如用户名 3–20 位且只含 `[A-Za-z0-9_]`、密码 ≥8 位、邮箱格式。
- 必须查库/问外部系统才能判断（依赖系统当前状态）→ **Service**。如用户名是否已被占用、密码是否匹配、用户是否已注销。

| 维度 | Schema 校验 | Service 校验 |
|---|---|---|
| 别称 | 输入契约 / 语法校验 | 业务规则 / 领域约束 / 语义校验 |
| 依赖外部状态 | 否 | 是 |
| 谁执行 | 框架（进 router 之前） | 我们的代码（拿到 `db` 之后） |
| 失败响应 | 422，且指明出错字段 | 409 / 401 等业务语义码 |
| 责任方 | 客户端写错（提示用于帮它改） | 业务冲突（提示用于说明为何不行） |
| 可否拿 session | 不能，也不该 | 可以 |
| 副作用 | 必须无 | 有（写库、抛领域异常） |

**本项目的三层校验（按「要不要问数据库」分化）**：

| 层 | 校验什么 | 性质 | 失败 |
|---|---|---|---|
| `schemas/auth.py` | 用户名长度/字符集、邮箱格式、密码长度 | 语法（无状态） | 422 |
| `services/user_service.py` | 用户名/邮箱是否已被占用 | 业务（有状态） | 409 |
| DB unique 约束 + `IntegrityError` | 并发下是否真的重复 | 数据完整性（最终兜底） | 409 |

> **与本节上方「唯一性三层」的关系**：上方那条讲的是**唯一性这一个点内部**的三层（前置 SELECT 给体验 / 唯一索引防脏数据 / 捕获 IntegrityError 避免 500）；此处讲的是**整条请求链**上的三层（Schema 语法 / Service 业务 / DB 完整性）。两者是**同一个纵深防御思想在两种粒度上的表述**，不冲突。

**为什么业务校验不能塞进 Schema**：① Schema 阶段拿不到 session，框架也不会给——强塞进去会让这个纯数据模型变成「有外部依赖、有副作用」的东西，丧失复用性；② Schema 是可跨场景复用的数据契约（未来后台批量导入用户可能复用同一个 `RegisterIn`），业务规则应随业务走，不该焊死在数据模型上。

**易混点澄清**：`UserOut` **不是校验**，是**出口的序列化白名单**。校验管「进门时检查来的人」，白名单管「出门时决定给别人看什么」——方向相反。

**面试口径（口语）**：「格式类的校验我放 Schema，不需要问数据库，框架在进业务层之前就挡掉了，返回 422 还带字段名；业务类的放 Service，比如用户名是否被占、密码对不对，必须查库才能判断，返回 409 或者 401。用户名这一个字段我实际校验了三遍——Schema 管格式、Service 管重名、数据库唯一约束兜并发。这三层不是重复，是纵深防御，每一层都假设上一层可能会漏。」
