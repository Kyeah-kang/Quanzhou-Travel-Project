## 关键设计决定

- `client` 使用 session 作用域并通过上下文管理器维护应用生命周期，减少重复创建。

- 鉴权测试继续走真实注册→登录→Bearer token 链路，没有使用 `dependency_overrides`，保留端到端证明能力。

### 老师讲解 / 我的复述记录

**老师讲解主线（本课题眼：测试工程 = 生产依赖注入的镜像）**：

1. **fixture ↔ `Depends` 同源**：D09 的 `Depends(get_current_user)` 与 D10 的 `def test_x(client, user_factory)` 是**同一个思想在生产侧/测试侧的两次落地**——调用方不构造依赖，只在签名里声明需求，由框架解析注入。唯一区别：`Depends` **显式**声明，fixture 靠**参数名匹配**、**隐式**解析（pytest 完全不看类型注解）。
2. **作用域的本质是隔离**：`client` 无状态（只是请求转发壳）→ `session`，省掉重复初始化；`user_factory` 有状态（内部维护 `created_usernames` 账本）→ `function`。**原则：能被测试改坏的状态，绝不允许跨用例共享。**
3. **yield teardown = 框架级保证的 `try/finally`**：写在 `conftest.py` 一处，全部用例自动获得；**中途断言失败也照跑**，这是「零残留」的实现手段。健壮的清理逻辑必须能容忍「要清理的东西其实不存在」（`_delete_users` 的空集短路）。
4. **工厂 fixture 是「产能」不是「产物」**：用例缺的不是「一个用户」，而是「**按需造用户的产能**」。`register=False` 的本质是区分**造数据**与**造身份**——重名冲突/未知用户这两个场景本就要求「这个用户不该存在」。
5. **不要 mock 掉正在测试的东西**：`dependency_overrides` 更快但更弱，会**划掉要考的题**。手法强弱须匹配测试目的（端到端 > override > 纯单元）。
6. **六道防线，两条白送**：`OAuth2PasswordBearer` 拦下「没带头」「头格式错」（框架层）；`decode_access_token` 与 `deps.py` 拦下「乱串/过期/非数字 sub/已删用户」（我们的代码）。**谁写的谁负责测**——故框架那两条只断言 401+header，自家四条要断言具体 `detail`。
7. **`with TestClient(app)` 比裸 `TestClient(app)` 更规范**：前者触发 FastAPI **lifespan**（启动/关闭钩子），将来加「启动预热模型、关闭释放连接池」时只有它能覆盖；后者**静默跳过 lifespan**——测试全绿、线上炸。
8. **技术债登记是判断力**：测试直连开发库是**有意为之的权衡**（正解=独立测试库+事务回滚，属上 CI 时必做项），记清「是什么 / 为何现在不做 / 何时还」。

评审发现（均低，不返工）：
1.（低·类型注解失真）测试里把 `user_factory` 标成 `Callable[..., object]`，转头又调 `.username`/`.headers`；为糊弄类型而写的 `assert hasattr(user, "username")`（`test_register.py:20-21、55-56`）是**无意义的断言噪声**。正解：把 `TestUser` 挪到可被双方 import 的位置（如 `tests/types.py`，或 `if TYPE_CHECKING: from tests.conftest import TestUser`），注解写 `Callable[..., TestUser]`，那几行 `hasattr` 一并删掉。AGENTS §2.2 要求类型注解有意义，教科书代码更不该留这种噪声。
2.（低·参数语义含糊）`include_email` 在 `register=False` 时**完全不起作用**（只在拼注册 payload 时读它），但 `test_register.py:54` 仍传了它——读代码的人会以为它改变了返回的 `email`。建议：要么该参数只在 `register=True` 语义下存在（删掉或加注释说明），要么让它在两种模式下都生效。
3.（低·记录）daily「发现与处理」第二条读起来像修了什么 bug，但没说清具体报的什么错。建议补一句现象（如 `ImportError` / 收集错误），否则后人无法复现这个教训。
