## 二、本日要解决什么问题 / 教学点

前 12 篇语料只活在 `data/` 里——**它们还不是"产品数据"**。M4 的 `/api/sites` 列表页、M5 的行程约束规划，读的都是 MySQL 的 `heritage_sites` 表。**今天就是让语料真正"进库"的那一天**，顺带把最后 7 处补完（22/22）。

教学点（老师精讲，本日深度=中，只精讲 ① ②）：
① **Alembic 增列迁移**：为什么上线后不能手改表？`upgrade`/`downgrade` 都必须能跑通——迁移脚本是**可回退的代码**，不是一次性 SQL；
② **幂等 upsert**：判定键是 `site_key`（唯一键）；存在则更新、缺失则插入。**连跑两次必须结果一致、行数不变**——这是"数据管线可重复运行"的最低要求，也是面试题「数据怎么更新？重跑会不会重复灌？」的直接答案；
③ `source` 为什么在 MySQL 只存**短引文**：完整来源列表留在语料与 PG metadata，MySQL 不重复存大字段，避免两处口径漂移；
④ **完整率 ≠ 完成率**：拿不到来源的字段要如实计入"待校对率"，而不是硬填一个数把它凑成 100%。

## 五、验收（backend/.venv 激活后执行，贴真实输出）

```
python -m alembic upgrade head          # 新列出现
python -m alembic downgrade -1          # 可回退，再 upgrade head 回来
python -m app.ingest.site_loader        # 第 1 次：全部 inserted
python -m app.ingest.site_loader        # 第 2 次：全部 updated/skipped，行数不变
python -m app.ingest.corpus_check       # 22 篇全 PASS，退出码 0
python -m pytest -q                     # 全绿（M1 的 24 + 语料的 + 新增）
python -m ruff check .
```
- 另附自证：
  1. **幂等对照**：两次运行的 `inserted/updated/skipped` 计数 + `SELECT COUNT(*)` 前后一致；
  2. **22/22 在库**：`SELECT COUNT(*), COUNT(DISTINCT site_key) FROM heritage_sites;` → `22, 22`；
  3. **完整率表**：22 × 字段的填充情况（`面积/category/name → 100%`；`lat/lng`、`open_hours`、`visit_duration_min`、`notice`、`key_element` 的**待校对率**如实分列）；
  4. **迁移可回退**：`downgrade` 后新列消失、`upgrade` 后回来。
