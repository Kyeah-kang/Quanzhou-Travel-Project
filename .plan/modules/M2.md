## 0. 一句话定位

M2 的产物**不是**"把 22 处资料塞进向量库"，而是**一套可复现、可校验、可评测的旅游领域数据底座**：
它是后续「可执行、可验证、可解释的文化旅行决策系统」的地基——检索要能被量化，数据要能支撑**硬约束**（开放时间/参观时长/区域/坐标/主题），而不只是"语义相似"。

**上游依赖**：M1（MySQL 主数据表 + 24 条测试基线）、M0（两库容器：mysql `127.0.0.1:3307`、pg `127.0.0.1:5432`）。
**下游消费**：M3（RAG 问答）、M4（`/api/sites` 列表页）、M5（行程约束规划）——见 §8。

## 1. M2 交付物（七项）

1. **22 处世遗点高保真结构化主数据**（语料 frontmatter → MySQL `heritage_sites`，含为 M5 预留的行程约束字段）
2. **语料资产**：站点语料 22 篇（统一六节结构）+ 主题文化语料 ≥6 篇
3. **统一规范**：frontmatter/metadata 规范（字段表 + 受控词表 + **溯源规则** + MySQL↔PG 双消费者映射）→ `docs/corpus-spec.md`
4. **可重复、可校验、可统计的 ingest 管线**：幂等 + stale 清理 + 边界校验 + 处理报告
5. **中文切分策略及对比实验**：3 策略 × 参数网格的**结构化对比数据**（先离线、不花 API）
6. **PG + pgvector 文档存储与索引**（`documents` + HNSW）+ **手写向量检索器**（余弦 + metadata 硬过滤）
7. **第一版离线检索评测集与结果**（`Hit@K` / `Recall@K` + 失败案例归类）+ **为 M5 预留的站点约束字段**（不实现行程 Agent）

## 2. M2 数据流总览

```
data/raw_md/*.md (frontmatter + 六节正文)
   │
   ├─[校验]→ app/ingest/corpus_check.py     结构校验（必填/词表/溯源自洽/六节齐全）
   ├─[质检]→ app/ingest/corpus_quality.py   填充率/来源覆盖/待校对/异说/字数节数 → data/reports/corpus_quality.json
   ├─[落主数据]→ app/ingest/site_loader.py  幂等 upsert → MySQL heritage_sites（第二消费者）
   └─[建索引]→ app/ingest/indexer.py
                    │  解析(frontmatter) → 切分(3 策略) → 嵌入(bge-m3) → 幂等 upsert
                    └→ PG documents(+vector 1024)  ── 报告 → data/reports/ingest_report.json

data/eval/retrieval_eval_v1.jsonl ──[评测]→ app/ingest/evaluator.py
                    │  调 app/rag/vector_store.search()
                    └→ Hit@K / Recall@K × {3 策略 × 过滤开关 × K∈3/5/10}
                        └→ docs/retrieval-eval.md + data/reports/eval_results.json
```

## 3. 关键设计决策（M2 新增 / 定稿，均需在对应 DNN 落地）

| # | 决策 | 理由 / 取舍 |
|---|---|---|
| D1 | **两类数据职责分离，且分工到字段级** | MySQL 存"可硬过滤/可约束"的结构化字段（区域/坐标/开放时间/参观时长/主题/注意事项）；PG 存"要语义召回"的正文分块 + 便于过滤的 metadata 镜像。**同一份 frontmatter 被两个消费者消费**，字段口径必须来自同一处（语料），不得各写各的。 |
| D2 | **溯源规则机器可校验**：文件级 `fact_status` + 字段级 `pending_fields` | `fact_status: 已核对` ⇔ `pending_fields: []`；数值字段无来源填 `null`、文本字段无来源填 `待校对`，**且字段名必须列入 `pending_fields`**。让"哪些是事实、哪些待校对"变成脚本能判的规则，而不是散文。 |
| D3 | **`documents` 表定稿**：`doc_type/doc_key/section/chunk_index/chunk_strategy/content_hash + embedding vector(1024)`，唯一键 `(doc_key, chunk_strategy, chunk_index)`，HNSW(cosine) | `doc_key` 统一站点与主题文档（站点文档的 `doc_key` == `heritage_sites.site_key`）；`section` 提供**跨策略稳定**的定位锚点。 |
| D4 | **`chunk_strategy` 进唯一键 → 多策略并存** | D19 要横比 3 种切分，若"重灌一次换一种"，既费 embedding 调用又无法同批评测；并存后**一次评测即可横比**。备选（重灌替换）已评估并放弃。 |
| D5 | **评测锚点用 `section` 而非 `chunk_index`** | 切分策略会改变块边界与序号，`chunk_index` 不稳定；`site_key + section` 在 3 种策略下都稳定 → 评测集可复用、可比。 |
| D6 | **PG 不纳入 Alembic，改由 `ensure_schema()` 幂等 DDL** | PG 的 `documents` 是**派生索引**（可从语料重建），不是权威数据；把第二套迁移体系引入教学模块收益低、复杂度高。**登记为技术债**：一旦 PG 承载权威数据，须补 Alembic。 |
| D7 | **Embedding 内容哈希缓存**（`data/.cache/embeddings/`，已在 `.gitignore`） | 同 `content_hash + model` 不重复调 API；让"重跑/换策略/重评测"趋近零成本、可离线复现。 |
| D8 | **先硬过滤，再向量召回** | 旅游场景的"能/不能"（开放时间、区域、时长）是**约束**，不该交给相似度；过滤与召回职责分离后，`empty_reason` 才能把"检索不到"和"被过滤掉"分开诊断。过滤后 ANN 可能不足 K 行（pgvector 已知行为）→ D18 实证 + over-fetch 应对，D19 量化。 |
| D9 | **`data/` 只放数据资产；Python 全部收进 `backend/`** | 一个 venv、无 `sys.path` 花招、校验器可被 pytest 直接测。`app/rag/` = 可复用领域能力；`app/ingest/` = 离线管线 CLI。**这是对原 D11 文件清单的修订**（原拟 `data/ingest/check_corpus.py`）。 |
| D10 | **M2 只调 Embedding，不调对话模型** | `bge-m3` 用于建索引与检索；任何 DeepSeek / LangChain QA / SSE / Agent 都属于 M3/M5，M2 一行都不写。 |

### D17 · pgvector 文档存储 + 嵌入管线闭环（幂等 / 边界 / 报告 / 缓存）
- **今日问题**：把语料变成**可检索的向量资产**，且这一步必须**可重复运行、可统计、可控**——不是"灌一次就完事"。
- **学习重点**：① `documents` 表与 HNSW 索引（`vector_cosine_ops`）的建立；② 嵌入调用（`httpx` → SiliconFlow `/v1/embeddings`，`BAAI/bge-m3`，**1024 维校验**）；③ **幂等三态**：`skip`（`content_hash` 未变）/ `update`（内容变）/ **`stale_deleted`**（新切分块少于旧块时清理尾巴）——这是"重复运行不产生失控重复数据"的关键；④ 边界校验：空内容、缺 `source`、维度不符、重复 chunk、`section` 缺失；⑤ 报告：总数/成功/失败/跳过/删除 + 失败原因分类；⑥ 缓存让重跑零 API 成本。
- **文件影响清单**：新增 `backend/app/db/pg.py`、`backend/app/rag/embedder.py`、`backend/app/rag/vector_store.py`、`backend/app/ingest/indexer.py`、`data/reports/ingest_report.json`；改动 `backend/app/core/config.py`（+`postgres_*`/`embedding_*`）、`backend/app/rag/__init__.py`、`backend/pyproject.toml`（+psycopg、httpx 提升运行时）、`.env.example`（+占位键）、`.plan/daily/<日期>-d17.md`；删除 **无**。
- **前置（学生执行）**：`.env` 补 `POSTGRES_*` 与 `EMBEDDING_API_KEY`（不入库）；批准 psycopg / httpx 两个依赖。

- **明确不做**：不写 LangChain（`PGVector`/`Retriever` 是 M3）；**不调任何对话模型**；不写检索接口（D18）；不改 MySQL。

### D18 · 手写 pgvector 检索器（余弦 + 硬过滤 + 诊断）
- **今日问题**：实现"能解释"的检索——为什么旅游场景**不能只靠向量相似度**，以及"先硬过滤再召回"的职责边界落在代码里的样子。
- **学习重点**：① `1 - (embedding <=> %s::vector)` 余弦相似度的 SQL 写法与参数绑定（显式 `::vector` 转换）；② **metadata 硬过滤**（`doc_key/area/category/theme/doc_type`）与向量的组合顺序；③ **过滤后 ANN 可能不足 K 行**：pgvector 已知行为 → `over_fetch`（先多取再过滤/截断）策略与实证；④ 诊断输出 `empty_reason ∈ {no_vector_match, filtered_out, low_similarity}` —— 把"没检索到"与"被过滤掉"分开；⑤ 为什么别名/专名、硬约束、多意图问题**不该**交给纯相似度（→ 引出 M3 的查询改写与 M5 的结构化约束）。
- **文件影响清单**：新增 `backend/tests/test_vector_store.py`（集成，PG 不可用时 skip）；改动 `backend/app/rag/vector_store.py`（+`search()` 与诊断）、`.plan/daily/<日期>-d18.md`；删除 **无**。
- **实现内容**：`search(query, top_k, filters, strategy, over_fetch)` → 结果 + 诊断；相似度阈值与 `low_similarity` 判定；过滤冲突（如 `area` 与 `doc_key` 互斥）→ `filtered_out`；单测（构造数据 + 边界）。
- **明确不做**：不加 rerank 依赖（只在文档里讨论，不装模型）；不接 LangChain；不做接口/路由；**不做评测汇总**（D19）。

- **验证命令**：`python -m pytest tests/test_vector_store.py -q`；手工脚本跑 3 条 query 贴结果。
- **深度证据**：**过滤 vs 纯向量**的对照输出 + 过滤后召回不足的实证记录 + `empty_reason` 诊断样例。
- **依赖**：D17 的索引数据；D16 的策略参数；产出是 D19 的被测对象。
