## 二、本模块要解决什么问题 / 教学点
D06–D09 每个模块各写各的测试，出现了「同一个 helper 抄三遍」和「同一个 `TestClient` new 四遍」。D10 把这些公共物收进 `conftest.py`，同时把 M1 的边界用例补齐，最后跑一次全量回归——这是 M1 的收口动作。
教学点（老师精讲、代码落地到 `conftest.py`）：① **pytest 的 fixture 机制**：`conftest.py` 是"自动发现的共享仓库"，测试函数只要把 fixture 名写进参数就能拿到值——和 D09 的 `Depends` 是**同一个思想在测试侧的翻版**（声明"我要什么"，框架负责给）；② **fixture 的作用域**（`session` vs 默认 `function`）与**yield 式 teardown**：`yield` 之前是准备、之后是清理，等价于 `try/finally` 但由框架保证执行——测试中途断言失败也不会漏清理；③ **工厂 fixture**：为什么 `user_factory` 返回"一个可以反复调用的函数"而不是直接返回一个用户（因为有的用例要造两个用户，比如重名冲突）；④ **测试金字塔与测试隔离**：用例之间不许有顺序依赖，每个用例自造数据、自清理；⑤ **为什么不用 `app.dependency_overrides` 伪造登录态**：本项目的 `/me` 测试走**真注册→真登录→真 token**，比 override 掉 `get_current_user` 更能证明鉴权链路真的通——override 是"更快但更弱"的手段，留到以后测与鉴权无关的接口时再用；⑥ **技术债登记**：测试目前直连开发库（靠唯一标识 + 事后清理），这是**有意为之的权衡**，记录在案，不本日解决。

## 四、交付物与验收

### conftest.py 提供
```python
@dataclass(frozen=True)
class TestUser:
    username: str
    email: str
    password: str
    id: int          # 注册接口返回的 id
    token: str       # 登录换到的 access_token
    @property
    def headers(self) -> dict[str, str]:   # 直接丢给 client.get(headers=...)

@pytest.fixture(scope="session")
def client() -> TestClient: ...            # 全测试共用，替代 4 处模块级 client

@pytest.fixture
def user_factory(client) -> Iterator[Callable[..., TestUser]]:
    """注册+登录一个唯一用户；teardown 时清理本次创建的全部用户。"""
```
- 唯一标识生成（原 `unique_identity`）、删用户（原 `remove_user`）**收进 conftest 作为私有 helper**，不再散落在各测试文件
- 清洗必须走 **yield teardown**（或等价），保证用例中途失败也不残留数据
- `conftest.py` 内不留任何未使用的 import

### 迁移与新增
- 4 个测试文件删除本地 `client` / `unique_identity` / `remove_user` / 内联注册登录样板，改用 fixture；**断言逐条保持等价**
- `test_register.py` 新增：**不传 email 也能注册**（email 为可选）→ 201 且 `email is None`
- `test_me.py` 新增：① **`sub` 非数字**（用 `settings.jwt_secret` 手工 `jwt.encode({"sub":"abc","exp":未来})`）→ 401「无效的访问令牌」；② **Authorization 头格式错**（`Authorization: Basic xxx`）→ 401（由 `OAuth2PasswordBearer` 短路，非我们的代码）
- `test_db.py`、`test_token.py` **不动**（前者不用 client，后者纯单元测试无 helper 重复）
